# Journal des micro-décisions

Décisions d'implémentation non couvertes explicitement par le coffre Obsidian, choisies au fil de l'eau (option la plus simple, sans bloquer), conformément aux instructions du projet.

- **2026-08-03 (Lot 0, ticket 0.2)** — Valeurs par défaut de `GameConfig` non fixées par le coffre : `gridCols` = 10, `gridAuto` = true, `showGridOnFog` = true, `showGridOnRevealed` = true, `qrUrl` = chaîne vide. Consigné aussi dans le coffre (`00 - Projet/Questions ouvertes.md`, Q5).
- **2026-08-03 (Lot 0, ticket 0.4)** — `vue-router` fixé en version 4.x (pas la 5.x, qui introduit des peer-dependencies Pinia hors du périmètre décidé T2/T3 « rester simple »).
- **2026-08-03 (Lot 0, ticket 0.6)** — `docker-compose.yml`, `docker-compose.dev.yml` et `docker-compose.test.yml` déclarent chacun un nom de projet Compose distinct (`tentaclaire`, `tentaclaire-dev`, `tentaclaire-test`) pour éviter toute collision de conteneurs/réseaux entre exploitation, dev et tests.
- **2026-08-03 (Lot 0, ticket 0.6)** — Les services `docker-compose.dev.yml`/`docker-compose.test.yml` tournent en root (image officielle, pas de Dockerfile dédié) : `npm ci` écrit dans des volumes anonymes `node_modules` (sans impact hôte), mais `npm run build` peut laisser des fichiers `dist/` root-owned dans l'arbre bind-monté. Limitation connue et acceptée pour rester simple ; si ça bloque un build en local juste après, nettoyer avec `docker run --rm -v "$(pwd)":/app -w /app alpine rm -rf shared/dist server/dist client/dist`.
- **2026-08-03 (Lot 1, ticket 1.2)** — Règle ESLint `@typescript-eslint/no-unused-vars` assouplie (`args: 'none'`) : `createGame(config, rng, now)` reçoit des dépendances injectées (rng, horloge) utilisées seulement à partir des tickets suivants (1.3+) ; seules les variables locales inutilisées restent détectées.
- **2026-08-03 (Lot 1, ticket 1.2)** — `handleInput(direction, pseudo)` : la fiche du lot liste `handleInput(direction)` mais l'événement `input_accepted` exige un pseudo pour le feed ; paramètre `pseudo` ajouté (introduit au ticket 1.3).
- **2026-08-03 (Lot 1, ticket 1.2)** — `resumed` n'est émis que pour `paused → running` (reprise après pause), jamais pour `reset → running` (premier lancement) : aucune spec écran/mobile ne prévoit d'overlay dédié pour ce cas.
- **2026-08-03 (Lot 1, ticket 1.2)** — Après tout retour à la case de départ (reset ou futur respawn), `facing` par défaut = `'down'` (valeur arbitraire non spécifiée par le coffre).
- **2026-08-03 (Lot 1, ticket 1.5)** — Les fantômes ne sont spawnés (et ne consomment le rng) que dans `reset()`, jamais dans l'état `idle` initial du constructeur : cet état est un placeholder jetable avant toute vraie réinitialisation, ça évite de gaspiller des tirages aléatoires dessus.
- **2026-08-03 (Lot 1, ticket 1.8)** — Couverture mesurée via `@vitest/coverage-v8` (provider v8, seuil 90 % lignes sur `server/src/engine/**`), script racine `npm run test:coverage`. Dossier `coverage/` ajouté au `.gitignore`.
- **2026-08-03 (Lot 2, ticket 2.1)** — `state_delta` construit par diff de snapshot (`realtime.ts`) plutôt que par rejeu des événements moteur fins ; `index.ts` scindé en `app.ts` (composition root réutilisable par les tests, écoute sur port éphémère) + bootstrap minimal.
- **2026-08-03 (Lot 2, ticket 2.5)** — Upload d'image trop volumineux renvoie **413** (Payload Too Large) plutôt que 400 : `@fastify/multipart` lève une erreur avec ce code dès que la limite `fileSize` est dépassée pendant `toBuffer()`, code HTTP plus précis que 400 pour ce cas, conservé tel quel.
- **2026-08-03 (Lot 2, ticket 2.7)** — Le test SIGTERM lance `src/index.ts` via le binaire `tsx` invoqué directement (chemin `node_modules/.bin/tsx`), pas via `npx tsx` : `npx` ajoute une couche de process qui empêchait le signal/l'exit code de remonter proprement au process de test.
- **2026-08-03 (Lot 3, ticket 3.5)** — `qrUrl` ajouté à `PublicConfig` (`shared/src/types.ts`) : absent du sous-ensemble d'origine (Lot 0) alors que c'est un champ C6-immédiat et que le ticket 3.5 exige explicitement de le lire côté écran (`config.qrUrl`) — sans ce correctif, le QR Code n'aurait jamais pu être généré.
- **2026-08-03 (Lot 3)** — Vérification navigateur : pas d'accès root sur `serveur_dev` pour installer les dépendances système de Chromium (`playwright install-deps` échoue, pas de sudo). Contournement : conteneur `mcr.microsoft.com/playwright` (déjà utilisé par `docker-compose.test.yml`) lancé avec `--network host` pour piloter Chromium et atteindre les serveurs dev tournant sur l'hôte (`localhost:3000`/`5173`).
- **2026-08-03 (Lot 4, ticket 4.1/4.4)** — `chaosCooldownMs` et `democracyWindowMs` ajoutés à `PublicConfig` (`shared/src/types.ts`) : même oubli que `qrUrl` au Lot 3 (ticket 3.5) — sans `chaosCooldownMs`, la manette ne peut normaliser `cooldownRemainingMs` en fraction 0..1 pour l'anneau de progression (ticket 4.4) ; `democracyWindowMs` sert au cadencement du libellé « Vote en cours ».
- **2026-08-03 (Lot 4, ticket 4.6)** — Aucun code supplémentaire nécessaire : la reconnexion transparente (bandeau, boutons grisés, reprise de session) était déjà entièrement portée par `useSocket` (ticket 4.1, correction du token de reconnexion) et `padDisabled` (ticket 4.5). Vérifié en gelant réellement le process serveur (`kill -STOP`/`-CONT`) ~50s : bandeau « Reconnexion… » apparaît après le timeout de ping Socket.IO (~45s, valeur par défaut non modifiée), pseudo/token identiques après reprise.
- **2026-08-04 (Lot 5, ticket 5.6)** — Bug de rendu Lot 3 corrigé (`boardRenderer.ts`) : `showGridOnFog`/`showGridOnRevealed` dessinaient chacun une grille pleine largeur superposée (l'une sous le brouillard, l'autre dessus), au lieu d'un quadrillage réellement dépendant de l'état par case — désactiver `showGridOnFog` seul restait sans effet visible, la grille « révélée » dessinée sous le brouillard semi-transparent restait visible en transparence. Remplacé par un tracé unique découpé par case (`Path2D` + `ctx.clip()`) au-dessus du brouillard, correctement indépendant pour chaque toggle. Non détecté au Lot 3 faute d'avoir testé les deux toggles désactivés indépendamment l'un de l'autre.
- **2026-08-04 (Lot 6, ticket 6.1)** — Sprites (personnage, fantômes) implémentés en primitives Canvas 2D paramétrées par thème plutôt qu'en fichiers SVG chargés en image : le renderer (Lot 3) dessine déjà tout directement dans la boucle `requestAnimationFrame`, sans pipeline de chargement d'image ; introduire de vrais SVG rasterisés ajouterait chargement asynchrone/cache/gestion d'échec pour un résultat équivalent, le tracé étant de toute façon écrit à la main dans les deux cas (aucun outil de génération d'image disponible). Respecte l'exigence fonctionnelle (silhouette D4 constante, 5 styles tranchés, perfs, aucun asset sous licence).
- **2026-08-04 (Lot 6, ticket 6.1)** — Un seul `client/src/themes/themes.css` (5 blocs `.theme-<id>`) plutôt que 5 sous-dossiers `themes/<id>/theme.css` : chaque bloc ne fait qu'une douzaine de variables CSS, les regrouper est plus simple à maintenir cohérent visuellement.
- **2026-08-04 (Lot 6, ticket 6.1)** — Polices Google Fonts embarquées via `@fontsource/*` (paquets latin uniquement : `latin-400.css`, pas les sous-ensembles cyrillique/grec/vietnamien non nécessaires en français), licence SIL Open Font License — aucun CDN à l'exécution, conforme à la contrainte.
- **2026-08-04 (Lot 5, ticket 5.2)** — Deux bugs corrigés (log rétroactif, absents à tort de ce journal au moment des commits) : (1) `launch()` n'adoptait jamais de config, seul `reset()` le faisait — si l'admin modifiait un champ non-immédiat après Réinitialiser mais avant de cliquer Lancer, le changement était perdu, contredisant C6 (« au prochain Réinitialiser ou Lancer »). `launch(config?)` adopte désormais la config depuis la phase `reset` uniquement (jamais depuis `paused`, pour ne pas perturber une reprise). (2) `useAdminApi.ts` posait toujours `Content-Type: application/json`, y compris sur les POST sans corps (launch/pause/reset/logout) — Fastify rejette un corps vide avec ce Content-Type (`FST_ERR_CTP_EMPTY_JSON_BODY`, 400), cassant ces quatre routes ; le header n'est plus posé que si un corps JSON existe réellement.
- **2026-08-04 (Lot 5, ticket 5.4)** — `gridRows` (mode auto) ne se recalculait qu'à l'activation d'une image, jamais quand l'admin changeait ensuite `gridCols` — corrigé : `PUT /api/admin/config` recalcule `gridRows` dès que `gridCols`/`gridAuto` change, si une image est active. `computeAutoGridRows` déplacé de `server/src/engine/grid.ts` vers `shared/src/grid.ts` (ré-export conservé côté serveur) pour que le client calcule le même aperçu sans dupliquer la formule. Proxy `/uploads` ajouté à `client/vite.config.ts` (manquant, seuls `/api`/`/socket.io` l'étaient) — sans lui les vignettes de galerie étaient cassées en `npm run dev`.
- **2026-08-04 (Lot 7, ticket 7.4a)** — Bug bloquant découvert en testant la build de production directement (`node server/dist/index.js`, jamais fait avant ce lot — tous les lots précédents vérifiaient via le serveur dev Vite, qui a son propre fallback SPA) : `/screen`, `/play`, `/admin` renvoyaient un 404 brut en navigation directe ou rechargement, `@fastify/static` ne servant que des fichiers réels. Le QR Code pointant vers une URL absolue (`/play`), un smartphone qui le scanne aurait reçu un 404 pur. Corrigé via `app.setNotFoundHandler()` : toute requête GET hors `/api/*`/`/uploads/*` sert `index.html`, laissant Vue Router router côté client (avec sa propre route 404 catch-all).
- **2026-08-04 (Lot 7, ticket 7.4b)** — `AdminView.vue` vérifiait l'authentification via un `GET /api/admin/config` volontairement voué à échouer (401) si non connecté — Chromium journalise toute requête fetch en échec comme erreur console, quelle que soit la gestion applicative (`catch` propre côté code). Nouvelle route `GET /api/admin/session` (toujours 200, `{ authenticated }`), exclue du garde d'authentification comme `/login`/`/logout`, remplace ce sondage par échec.
- **2026-08-14 (hors lot, demande directe d'Arnaud)** — Pilotage à chaud des réglages joueurs/fantômes : `IMMEDIATE_FIELDS` (`server/src/config.ts`) élargi à `movementMode`/`chaosCooldownMs`/`democracyWindowMs` (déjà dans `PublicConfig`, donc diffusables via `config_changed`) ; nouvelle liste `LIVE_ENGINE_FIELDS`, distincte, listant les six champs (les trois précédents + `ghostCount`/`ghostSpeed`/`ghostBehavior`) que `PUT /api/admin/config` répercute désormais sur `GameEngine.updateConfig()` en plus de `ConfigStore`. Deux listes plutôt qu'une : `ghostCount`/`ghostSpeed`/`ghostBehavior` n'ont aucune utilité à être rediffusés aux clients (hors `PublicConfig`, aucun rendu n'en dépend côté joueur/écran — seule la position réelle des fantômes, déjà diffusée via `state_delta`, compte). Périmètre volontairement restreint à ces six champs (ceux explicitement demandés) : grille, thème, point de départ, collision et rayon de torche restent C6 (prochain reset/launch), les toucher à chaud risquerait de désynchroniser un plateau déjà en cours (ex. `revealed` dimensionné pour l'ancienne grille).
- **2026-08-14 (hors lot, suite directe de 9.1)** — `scripts/loadTest.mjs` (ticket 7.3) débranché de toutes les routes admin à la demande d'Arnaud : plus de login/GET-PUT config/reset/launch, uniquement des connexions `player` (et `screen` en lecture pour `BOT_STRATEGY`), qui ne nécessitent aucune authentification côté serveur (`sockets.ts` : seules les routes REST `/api/admin/*` sont protégées, pas les rôles socket). Objectif explicite : laisser l'exploitant piloter/modifier la partie en direct depuis `/admin` pendant le test (c'est justement l'intérêt du pilotage à chaud du 9.1), sans que le script ne vienne écraser ou réinitialiser quoi que ce soit. Corollaire : plus rien à sauvegarder/restaurer avant/après (l'ancienne version snapshotait la config), donc le script peut être interrompu au `Ctrl+C`/`SIGTERM` à tout moment sans laisser la partie dans un état à nettoyer. `BOT_STRATEGY=nearest|density` calculés par un unique connecteur d'observation (rôle `screen`) plutôt que par chaque joueur simulé individuellement : le personnage est unique et partagé (vote/input collectif), donc une seule direction "optimale" par instant a du sens — la calculer une fois et la faire lire par tous les bots évite `PLAYER_COUNT` recalculs redondants sur le même état.
